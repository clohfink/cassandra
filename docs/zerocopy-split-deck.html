Zero-copy
SSTable splits

Splitting an SSTable by token range without decompressing, without deserializing a single row, and — on a reflink filesystem — without writing the data at all. The same synthesis now puts a partial transfer back on the zero-copy streaming path.

335× faster 1,125× fewer bytes written 277× less heap 160× less CPU 63 GiB parent · 8 ways · cold cache + partial zero-copy streaming
01
The problem

Incremental repair has to rewrite whatever it touches

  • Repair marks data repaired at SSTable granularity. An SSTable holding both repaired and unrepaired partitions must be split first — that is anticompaction.
  • Anticompaction is implemented as a compaction: read every row, decompress it, deserialize it, re-serialize it, re-compress it, write it out. Cost is proportional to the data.
  • STCS and TWCS build very large SSTables that span the whole ring. One 63 GiB file costs 258 seconds of rewrite — and 148 seconds of CPU. At the measured 4.1 s/GiB, a 1 TiB file is ~70 minutes — per file, per node, per repair.
  • So operators turn incremental repair off on exactly the tables that need it most, or accept repair windows that never close.

The insight

The bytes are already in the right order

04
The design

Copy chunk runs · rebuild only the index

never touched at all

  • Decompression — not one chunk is inflated
  • Row and cell deserialization — no object graph is ever built
  • Re-serialization and re-compression
  • Per-chunk CRC32 recomputation — they ride along in the bytes

one pass over Index.db

  • Rewrite one varint per partition: its data position, minus a constant
  • Bloom filter, index summary, partition-size histogram, cardinality — all fall out of the same pass
  • Statistics.db is copied with four fields recomputed
  • Index.db is 1–3% of the data, and it is the only thing read end to end

That alone makes the split CPU-cheap: on a 63 GiB parent, the rewrite churns 69.6 GiB of heap materialising rows and burns 148 s of CPU; the split churns 257 MiB, burns 0.9 s, and never materialises a single row.

The second win

On xfs, don't copy the bytes at all

06
The third win

With the copy gone, one full read was left

  • Digest.crc32 is a checksum over every physical byte of the child — so producing it means reading the whole child back. Once the extents are shared, that is the entire remaining cost of a split.
  • Nothing requires the component. Opening an SSTable needs Data, Index and Statistics; entire-SSTable streaming skips files that don't exist; the backup manifest enumerates what is there and restore never asks for it.
  • A compressed SSTable is already self-checking without it — every chunk carries an inline CRC32 that the split preserves and that every read verifies.
  • So it is now optional: zero_copy_split_digest_enabled: false.
The honest cost, and why we pay it. Verifier is its one reader, and a missing digest is not an error there — it upgrades to a full extended verification instead. So nodetool verify and import --verify-sstables get slower, not weaker, for those children. It therefore ships defaulting to on for upstream — but we don't run nodetool verify, so we turn it off. Every headline number in this deck is that configuration: reflink on, digest off.

63 GiB parent · split 8 ways

Virtually zero disk growth

new bytes on disk 57 MiB was 64,140 MiB — the children exist without the data being duplicated
write amplification 0.0009 was 1.0002 — index and metadata only
heap churned 257 MiB was 69.6 GiB — nothing materialises a row
  • The headroom requirement disappears. Anticompaction no longer needs free space for a second copy of the largest SSTable on the node — which is its own operational blocker on a full disk.
  • SSD endurance is spared the write entirely, and page cache is spared the pollution.
  • Cost of the alignment that makes sharing possible: 224 KiB of padding across all eight children of a 63 GiB parent — and it does not grow with the data, only with the child count.
09
Why "no deserialization" is the load-bearing part

The rewrite's cost tracks rows, not bytes

rewrite 8.2 GiB parent

  • 74.1 s and 19,807 MiB of heap
  • Same byte count as the corpus above it, but 4× the rows — and it costs 2× the time
  • A composite UUID key changed it by 0.7%: what matters is how many rows have to be materialised, not how heavy each key is

zero-copy same parent

  • 0.81 s and 293 MiB of heap
  • Row count is invisible to it — the bytes are opaque
  • What little it does scale with is the partition count, because that is the size of Index.db

This is the win that does not depend on the filesystem. Reflink removes the I/O; never deserializing removes the CPU. Wide-row and small-row tables — the ones where a rewrite hurts most — benefit most.

10
Consumer one · where it lands today

Anticompaction stops being the reason repair is off

before rewrite path

  • Repair session waits on a full rewrite of every mixed SSTable
  • Cost scales with the largest file on the node
  • Needs free space for a second copy
  • Competes with real compaction for CPU and throughput budget

after zero-copy split

  • Cost scales with Index.db, not with the data
  • No decompression, no row materialisation, no new bytes
  • Still a first-class compaction: shows in compactionstats, bounded by compaction_throughput, stoppable by nodetool stop
  • Falls back to the unchanged rewrite whenever it cannot apply
The gate. Every partition is labelled full / transient / unrepaired by token from one Index.db pass. The split applies when each of those occupies at most one contiguous run — the common unrepaired · full · unrepaired shape. Interleaved ranges, which is what many vnodes produce, are ineligible and take the old path. Nothing is forced.
11
Where it pays most

STCS and TWCS, where one file can be the whole problem

  • STCS merges same-size files repeatedly, so the top tier is a few enormous SSTables that each span the whole ring — every one a mixed SSTable at repair time, each costing a full rewrite.
  • TWCS compacts each window into one large file — so anticompaction rewrites data whose whole point was to be immutable and expire together.
  • So the practical answer has been to avoid incremental repair on exactly these tables, pushing them onto full repair and overstreaming instead.
  • With the split, the cost of the same operation is proportional to the index. A 63 GiB TWCS file goes from 258 s and 63 GiB of writes to 0.8 s and 57 MiB.
One behaviour change to accept. A verbatim copy cannot purge tombstones: children retain what a rewrite would have dropped. Retention only — nothing is resurrected, and a later compaction purges it. Gated by zero_copy_anticompaction_enabled.
12
Consumer two · the same primitive, a different caller

Zero-copy streaming had the same all-or-nothing rule

  • Entire-SSTable streaming takes the cheap path only when the requested sections cover the whole SSTable — contained() measures the transfer span against uncompressedLength(). Ask for a subset of tokens and every byte goes the row-by-row way.
  • With vnodes, a subset is the normal case. A joining node's ranges are a small fraction of any given SSTable, so nearly every bootstrap, decommission, rebuild, removenode and repair transfer is partial.
  • And they are the same files as the slide before — a whole-ring STCS or TWCS SSTable is never contained in one peer's ranges.
  • The split made this worse before it made it better: a child's first partition is not at byte 0, so its span falls short of uncompressedLength and a perfectly good SSTable lost its eligibility. The predicate now measures from the first indexed partition, so children ship verbatim again — that fix alone is why the split does not cost you zero-copy streaming.
And the bill is not where you would guess. For a compressed SSTable the sender is already cheap: CassandraCompressedStreamWriter ships whole compression chunks verbatim. It is the receiver that decompresses, deserializes, re-serializes and recompresses every row, then rebuilds Index, Filter and Summary from scratch. What partial streaming removes is CPU and GC, not I/O.

14
Where the saving actually is

The receiver stops rebuilding what it could be handed

before row-by-row receive

  • CompressedInputStream over the socket, a seek per section, writePartition per partition
  • Every row decompressed, deserialized, re-serialized, recompressed
  • Index, Filter and Summary rebuilt from nothing
  • Cost tracks rows — the same bill as the anticompaction rewrite, paid on the other node

after slice on the entire-SSTable path

  • writeComponent(type, in, length) per component; not one byte is inspected
  • Data.db leaves by sendfile, one range per run, straight off the parent's fd
  • Index, CompressionInfo, Statistics, Summary and Filter arrive already built for the range
  • Digest.crc32 is the one thing the sender does not produce — on this path the bytes never enter its process — so the receiver CRCs Data.db as it writes it
What the sender now pays — and what nobody has measured. Synthesis is new work per SSTable: two Index.db passes scoped to the slice, a filter and summary build, five small component writes with fsyncs, all under the same lock a stats mutation takes. There is no benchmark for partial streaming, in either direction. A bootstrap over thousands of narrow-range SSTables could be net slower; the receiver-side saving is a code-path argument, not a number.
15
The price and the guardrails

Dead space is the cost, and a flag bounds it

  • A cell cannot be cut, so a slice carries a dead prefix and — new here — interior gaps, where two sections sit less than a cell apart. Nothing indexes them, so nothing reads them; they are transferred and stored for nothing until the next compaction.
  • Roughly one chunk per section boundary: immaterial for a wide range, dominant for a narrow one — a 4 KiB section inside a 16 KiB chunk is 75% dead. zero_copy_partial_stream_max_dead_space_ratio: 0.25 refuses anything worse, which is also why narrow repair-mismatch ranges are the likeliest to be turned away.
  • A dozen gates, every one before the first byte reaches the socket. Non-BIG format, legacy counter shards, unusable parent metadata, too many runs, too much dead space, or a synthesis failure — each falls back to the unchanged row-by-row path. Nothing on the wire changed: a slice's header is byte-shaped exactly like a whole SSTable's.
  • Counted: PartialZeroCopyStreamsOut, PartialZeroCopyStreamsFailed, PartialZeroCopyStreamDeadBytes.
The mixed-version hazard. What lands on the peer begins with a dead prefix, and an unpatched Verifier throws when the first indexed partition is not at byte 0 — nodetool verify fails and marks the SSTable unrepaired. Those are the same two seeks the splitter needed. So zero_copy_partial_stream_enabled stays off until every node that can receive has them.

17
Nothing here risks data

The four things we accepted

  • Tombstones are retained, not purged. The children keep what the parent held; a later ordinary compaction drops it. Retention, never resurrection. A slice purges nothing in transit either.
  • Per-SSTable statistics are inherited, not recomputed. Row and cell totals cannot be derived without deserializing, so each child inherits the parent's — and so does a streamed slice. Every error is in the conservative direction; it costs metric accuracy.
  • A little dead space. Up to one compression chunk of dead bytes per child end, plus ≤64 KiB of alignment padding per child when extents are shared; a slice adds interior gaps, bounded by a flag.
  • Extent sharing is filesystem-conditional, and du over-reports shared blocks until the parent is unlinked. Discovered by trying; silently absent elsewhere.

Every one of these is a metrics or scheduling cost, paid until the children are compacted normally, in exchange for not reading a single row.

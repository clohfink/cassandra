Zero-copy SSTable splitting

Splitting an SSTable today is a full compaction: every byte is decompressed, every cell is deserialized into an object graph, re-serialized, and re-compressed. Almost none of that work is necessary. This is how we split by copying compression chunks verbatim instead — and where it is wired into anticompaction.

2 · The constraint that shapes everything

A compressed Data.db is a bare run of [chunk payload][4-byte CRC32] records. All addressing lives in CompressionInfo.db, and the mapping from an uncompressed position to a chunk is pure integer division: 

// CompressionMetadata.java:237
long idx = 8 * (position / parameters.chunkLength());

There is no per-chunk uncompressed length stored anywhere. The grid is implicit. Only the final chunk may hold fewer than chunkLength uncompressed bytes.

Why you cannot re-encode the first chunk

The intuitive design is: start the child at the exact split partition, recompress that partial head chunk, then copy the rest. It does not work. If chunk 0 of the child holds fewer than L uncompressed bytes, then every subsequent chunk is desynchronised from the division — position / L now points at the wrong chunk, and the bytes at the tail become unaddressable.

3 · The design: copy a chunk run, tolerate dead bytes

Instead of moving the split point to a chunk boundary, move the chunk boundary to wherever it already is. Start the child at the chunk containing the first partition, and accept that the child's Data.db opens with a few bytes belonging to the previous partition. Nothing points at them, so nothing reads them. 

i     = lo / L                 // first chunk, inclusive
j     = (hi - 1) / L           // last chunk, inclusive  — note (hi-1), not hi
C     = j - i + 1              // child chunkCount
from  = O(i),  to = O(j + 1)   // byte range in the parent Data.db
Fp    = to - from              // child physical length, exact
Dp    = hi - i * L             // child dataLength
shift = i * L                  // subtracted from every index position

assert (C - 1) * L < Dp <= C * L;
Trailing slack is forbidden, leading slack is fine. getPositionsForRanges uses uncompressedLength() as its right bound and the stream reader deserializes exactly that many bytes, so a child's dataLength must be trimmed to the end of its last live partition. A dead prefix is harmless because every local read path enters Data.db only at a position read from the index.

4 · Rebuilding the index without touching the data

A primary index record is a key followed by two varints and an opaque blob. Only the first varint — the absolute data-file position — needs to change:

Everything else falls out of one index pass

The decisive observation is that Index.db already holds every partition key in token order and every partition's data-file position. That is enough to rebuild the filter, the summary and an exact partition-size histogram — and Cassandra already does precisely this walk on every load when a summary is missing:

5 · Wiring it into anticompaction

Anticompaction after a repair splits an SSTable into repaired-pending and unrepaired parts. Today that is three SSTableRewriters routing each partition by token. The zero-copy path is carved out ahead of them, inside the existing per-group transaction, and only for SSTables whose labels form contiguous runs.

The failure mode that matters is not a crash — it is silence. If an SSTable were handled by neither path, data the repair session believes is pending would quietly stay unrepaired. So the integration asserts a strict set partition (handled ⊎ remaining == group) and throws rather than continue; any per-SSTable failure falls back to the rewrite, never skips.

What the numbers do and don't say

  • 2.1×–3.4× wall clock, 10×–60× less allocation. The allocation collapse is the more robust result: it follows mechanically from never building a row/cell object graph, and is far less machine-dependent than the timing ratio.
  • Write amplification is unchanged (1.008–1.024 vs 1.009–1.026). This is a CPU and GC win, not an SSD-endurance win.
  • The read column is modelled, not measured — /proc/self/io does not exist on macOS, so the harness says so rather than inventing a figure.
  • Zero-copy currently reads ~2× what it needs, because the digest is a separate second pass over the finished child. Folding the CRC into the copy loop would roughly halve it.
  • Single laptop, single-threaded, no JMH, warm page cache. Treat the ratios as indicative and the absolute latencies as meaningless for production.

7 · What it costs

Two deliberate trade-offs, none of which risk data loss:

CostDetail
No tombstone purge The rewrite path purges droppable tombstones by default and, because groups merge through one iterator, also collapses overwritten cells. A verbatim copy does neither. Retention only — never resurrection: reads apply withoutPurgeableTombstones at consumption time, and pendingRepair → repairedAt promotion is metadata-only, so retained tombstones ride into the repaired set and are purged by a later ordinary compaction.
Duplicated boundary chunk One chunk is shared between adjacent children, plus up to L dead bytes per child. At a 16 KiB chunk this is ~0.01–0.03%.

Three checks were taught about dead prefixes. Scrubber and Verifier each had an explicit first position == 0 assertion; both now seek to the first indexed position instead — worth noting that this loosens a corruption check for all SSTables, not only children. The third is CassandraOutgoingFile.contained(), the entire-SSTable zero-copy streaming gate: it used to demand transferLength == uncompressedLength(), which a dead prefix can never satisfy, and so refused the fast path on freshly-split children until a later recompaction. It now measures the requested span against the live data (uncompressedLength() − firstPosition), so a dead-prefix child streams whole — every component copied verbatim, exactly as it is read locally — without waiting to be recompacted. For an ordinary SSTable firstPosition == 0 and the check is unchanged.
